# HashMap

---

## 🔹 Хэш-таблица vs HashMap — в чём разница

Прежде чем разбирать HashMap, важно понять два уровня абстракции.

**Хэш-таблица** — это абстрактная концепция структуры данных. Идея: храни пары ключ-значение и находи значение по ключу за O(1), используя хэш-функцию для превращения ключа в индекс массива. Это "чертёж".

**HashMap** — конкретная реализация этой концепции в Java. Внутри — массив бакетов, объекты Node, load factor, treeify при 8 нодах и т.д. Это "здание по чертежу".

В других языках та же идея реализована по-своему: в Python — `dict`, в Go — `map`, в C++ — `unordered_map`. Детали разные, концепция одна.

---

## 🔹 Зачем нужна HashMap — проблема массива

Массив хранит элементы по **числовым индексам**. Чтобы достать элемент — нужно знать его номер. Быстро — O(1), — но неудобно: в реальных задачах хочется искать по **смысловому ключу**: по имени, по строке, по объекту.

Можно хранить пары (ключ, значение) в обычном массиве и искать перебором — но тогда поиск O(n). При миллионе элементов это катастрофа.

> [!note] Задача HashMap Хранить пары **ключ → значение** и находить значение по ключу за **O(1)**, даже если ключ — строка, объект или что угодно другое.

## 🔹 Ключевая идея: превратить любой ключ в число

Память компьютера работает быстро только с числами — числовой индекс позволяет мгновенно обратиться к нужной ячейке. Значит, нужно уметь **превращать любой ключ в число**.

Именно этим занимается **хэш-функция** — она берёт произвольный объект и возвращает целое число, **хэш-код**.

```
hash("apple")   →  92029210
hash("banana")  →  -1396355602
hash("cherry")  →  -1643467785
```

Затем по этому числу вычисляется **номер бакета** во внутреннем массиве:

```
номер бакета = hashCode % количество_бакетов
```

Итоговая цепочка:

```
put("apple", 5)  →  hash("apple") → 92029210 % 16 = 10  →  table[10] = 5
get("apple")     →  hash("apple") → 92029210 % 16 = 10  →  return table[10]  →  5
```

> [!tip] Почему это O(1) Вычисление хэша и взятие остатка — несколько арифметических операций. Обращение к массиву по индексу — одна инструкция процессора. Скорость не зависит от количества элементов.

## 🔹 Хэш-функция и контракт hashCode + equals

В Java каждый объект имеет метод `hashCode()`. Для стандартных типов он уже реализован. Для своих классов — нужно переопределять.

Хорошая хэш-функция:

- **Детерминированная** — один и тот же ключ всегда даёт одинаковый хэш. Иначе положишь элемент, а найти не сможешь.
- **Равномерно распределяющая** — разные ключи дают разные хэши. Если все ключи дают одно число — все элементы свалятся в один бакет и поиск деградирует до O(n).
- **Быстрая** — O(1).

```java
// Стандартные типы — hashCode() уже реализован
"hello".hashCode()  // -1220993920
42 .hashCode()      // 42

// Свой класс — нужно переопределить hashCode() И equals()
class User {
    String name;
    int age;

    @Override
    public int hashCode() {
        return Objects.hash(name, age); // стандартный способ
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User)) return false;
        User u = (User) o;
        return age == u.age && Objects.equals(name, u.name);
    }
}
```

> [!warning] Контракт: hashCode + equals всегда вместе HashMap сначала ищет бакет по хэшу, потом проверяет совпадение ключа через `equals()`.
> 
> Если переопределил только `hashCode()` — два одинаковых объекта попадут в один бакет, но `equals()` скажет что они разные → в мапе будут дубли. Если переопределил только `equals()` — два логически равных объекта дадут разные хэши → попадут в разные бакеты → `get()` не найдёт элемент.
> 
> **Правило:** равные объекты обязаны давать одинаковый хэш. Обратное необязательно.

## 🔹 Коллизии — неизбежная проблема

**Коллизия** — два разных ключа попадают в один бакет. Это случается по двум причинам:

1. Хэш-коды совпали (плохая хэш-функция или математическое совпадение).
2. Хэш-коды разные, но остаток от деления на размер таблицы одинаков.

```
hash("свиток") % 4 = 0
hash("золото") % 4 = 0   ← разные хэши, но один бакет → коллизия
```

Коллизии неизбежны математически: хэш-код — int, то есть около 4 млрд вариантов. Если элементов больше — коллизии гарантированы. Задача не устранить их, а **обрабатывать правильно**.

### Как Java решает коллизии — Chaining (цепочки)

Каждый бакет хранит не одно значение, а **односвязный список** нод. При коллизии новая нода добавляется в хвост списка.

```
table[0] → Node("свиток", A) → Node("золото", B) → null
table[1] → Node("меч", C) → null
table[2] → Node("зелье", D) → null
```

При поиске `get("золото")`:

1. Вычислили бакет → `table[0]`
2. Первая нода — "свиток". `equals("золото", "свиток")` → false. Идём дальше.
3. Вторая нода — "золото". `equals()` → true. Возвращаем значение.

> [!note] Чем опасна плохая хэш-функция Если хэш-функция всегда возвращает одно число — все элементы окажутся в одном бакете. Структура вырождается в связанный список, поиск становится O(n). Хорошая хэш-функция распределяет элементы **равномерно** по всем бакетам.

## 🔹 Внутреннее устройство HashMap

### Структура Node

Внутри HashMap — массив `Node[] table`. Каждый элемент массива — объект Node:

```java
class Node<K, V> {
    int hash;        // хэш ключа
    K key;           // ключ
    V value;         // значение
    Node<K,V> next;  // ссылка на следующий узел (для цепочки при коллизии)
}
```

```
table[] = [ null, Node, null, Node, null, Node, null ... ]  ← 16 ячеек по умолчанию
                   │
              Node{hash=..., key="меч", value=C, next=null}
```

### Параметры по умолчанию

|Параметр|Значение|Смысл|
|---|---|---|
|`DEFAULT_INITIAL_CAPACITY`|**16**|Начальный размер массива. Всегда степень двойки — это важно для оптимизации.|
|`DEFAULT_LOAD_FACTOR`|**0.75**|При заполнении 75% таблица расширяется. Баланс скорость/память.|
|`TREEIFY_THRESHOLD`|**8**|Список в бакете → красно-чёрное дерево при ≥ 8 нодах.|
|`UNTREEIFY_THRESHOLD`|**6**|Дерево → список обратно при ≤ 6 нодах.|
|`MIN_TREEIFY_CAPACITY`|**64**|Treeify только если вся таблица содержит ≥ 64 элементов. Иначе — просто resize.|

### Как вычисляется номер бакета (оптимизация)

Наивный способ: `hashCode() % capacity`. Работает, но операция деления медленная.

Так как `capacity` всегда **степень двойки**, деление заменяется быстрой побитовой операцией:

```java
int bucket = hash & (capacity - 1);  // эквивалентно hash % capacity, но быстрее
```

Но есть нюанс: `& (capacity - 1)` использует только **младшие биты** хэша. Старшие биты игнорируются → лишние коллизии, если объекты различаются только в старших битах.

Решение — перемешать биты перед вычислением бакета:

```java
static final int hash(Object key) {
    int h = key.hashCode();
    return h ^ (h >>> 16);  // XOR хэша со сдвинутым на 16 бит
    // "подмешивает" старшие биты в младшие → меньше коллизий
}
```

### Жизненный цикл put()

```
map.put(key, value)
  │
  ├─ 1. Вычислить hash(key)  →  h ^ (h >>> 16)
  ├─ 2. Найти бакет:  i = hash & (n-1)
  │
  ├─ 3. Бакет пуст?  →  создать Node, положить. Готово.
  │
  ├─ 4. Первая нода — тот же ключ?  →  перезаписать value. Готово.
  │
  ├─ 5. Бакет уже дерево?  →  вставить в красно-чёрное дерево.
  │
  ├─ 6. Бакет — список  →  идти по цепочке:
  │       ├─ нашли тот же ключ?  →  перезаписать value
  │       └─ дошли до конца  →  добавить Node в хвост
  │              └─ список стал ≥ 8 нод  И  таблица ≥ 64 эл.  →  treeify()
  │
  └─ 7. size > capacity × 0.75  →  resize()
```

### Rehash (resize) — расширение таблицы

Когда заполненность превышает `capacity × loadFactor` (по умолчанию 16 × 0.75 = **12 элементов**):

1. Создаётся новый массив в **2 раза больше** (16 → 32 → 64 …)
2. Все существующие ноды **перераспределяются** — номер бакета пересчитывается с новой capacity
3. Добавляется новый элемент

Это **O(n)** операция. Если знаешь размер заранее — задавай capacity сразу:

```java
// Хочешь хранить ~100 элементов без лишних rehash:
// нужная capacity = 100 / 0.75 ≈ 134 → следующая степень двойки = 256
Map<K, V> map = new HashMap<>(256);
```

### Оптимизация коллизий: список → дерево (Java 8+)

```
Нод в бакете < 8     →  хранить как односвязный список   (поиск O(n))
Нод в бакете ≥ 8     →  превратить в красно-чёрное дерево (поиск O(log n))
Нод в бакете ≤ 6     →  вернуть обратно в список (при удалениях)

Условие treeify: нод ≥ 8  И  вся таблица ≥ 64 элементов
Если таблица маленькая — лучше просто resize, чем строить дерево
```

> [!tip] Итоговые сложности
> 
> |Случай|put / get / remove|
> |---|---|
> |Хорошая хэш-функция, нет коллизий|**O(1)**|
> |Коллизии, список в бакете|O(n) в худшем|
> |Коллизии, дерево в бакете (Java 8+)|**O(log n)** в худшем|

## 🔹 Ключи уникальны, значения могут повторяться

HashMap не хранит два элемента с одинаковым ключом. Если добавить пару с уже существующим ключом — старое значение заменяется новым.

```java
map.put("зелье", A);
map.put("зелье", B);  // A удалено → map.get("зелье") == B
```

Значения могут повторяться — они не участвуют в поиске:

```java
map.put("зелье", зелье_здоровья);
map.put("хилка", зелье_здоровья); // одно и то же значение — ок, ключи разные
```

## 🔹 Потокобезопасность

HashMap **не синхронизирована**. При одновременном доступе из нескольких потоков — повреждение данных.

```java
// ❌ Опасно в многопоточной среде
Map<K, V> map = new HashMap<>();

// ✅ Простая синхронизация
Map<K, V> map = Collections.synchronizedMap(new HashMap<>());

// ✅ Лучший вариант (высокая производительность в многопоточке)
Map<K, V> map = new ConcurrentHashMap<>();
```

## 🔹 API — основные методы

```java
Map<String, Integer> map = new HashMap<>();

// Добавление / получение
map.put("apple", 5);                         // добавить или перезаписать
map.get("apple");                            // → 5, или null если нет ключа
map.getOrDefault("pear", 0);                // → 0 (безопасно, без null)

// Проверка
map.containsKey("apple");                   // → true,  O(1)
map.containsValue(5);                       // → true,  O(n) — проходит всю таблицу!
map.size();
map.isEmpty();

// Удаление
map.remove("apple");                        // удалить по ключу
map.remove("apple", 5);                     // удалить только если ключ=apple И значение=5

// Умные методы
map.putIfAbsent("apple", 3);               // добавить только если ключа нет
map.merge("apple", 1, Integer::sum);        // apple = старое + 1 (или 1 если нет ключа)
map.compute("apple", (k, v) -> v == null ? 1 : v + 1); // то же, но гибче
map.computeIfAbsent("apple", k -> new ArrayList<>()); // создать значение если нет ключа

// Итерация
for (Map.Entry<String, Integer> e : map.entrySet()) {
    System.out.println(e.getKey() + " = " + e.getValue());
}
map.forEach((k, v) -> System.out.println(k + " = " + v)); // через лямбду
```

### Подсчёт частоты — классический паттерн

```java
String[] words = {"a", "b", "a", "c", "b", "a"};
Map<String, Integer> freq = new HashMap<>();

for (String w : words) {
    freq.merge(w, 1, Integer::sum);
    // эквивалентно: freq.put(w, freq.getOrDefault(w, 0) + 1);
}
// freq = {a=3, b=2, c=1}
```

## 🔹 HashMap vs LinkedHashMap vs TreeMap

||HashMap|LinkedHashMap|TreeMap|
|---|---|---|---|
|Порядок|Нет гарантий|Порядок вставки|Отсортирован по ключу|
|get / put|O(1)|O(1)|O(log n)|
|Null ключ|✅ один|✅ один|❌|
|Когда использовать|Быстрый поиск|Нужен порядок вставки|Нужна сортировка|

```java
// LinkedHashMap — помнит порядок вставки
Map<String, Integer> linked = new LinkedHashMap<>();
linked.put("b", 2);
linked.put("a", 1);
// итерация: b=2, a=1

// TreeMap — ключи всегда отсортированы
Map<String, Integer> tree = new TreeMap<>();
tree.put("b", 2);
tree.put("a", 1);
// итерация: a=1, b=2
tree.firstKey();   // "a"
tree.lastKey();    // "b"
tree.headMap("b"); // все ключи < "b"
```

## 🔹 Типичные задачи

### Two Sum — найти два числа, дающих в сумме target

```java
// Идея: для каждого числа проверяем, есть ли уже нужный complement в мапе
// Это O(n) вместо O(n²) перебора двух вложенных циклов
int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>(); // число → его индекс
    for (int i = 0; i < nums.length; i++) {
        int complement = target - nums[i];
        if (seen.containsKey(complement)) {
            return new int[]{seen.get(complement), i};
        }
        seen.put(nums[i], i);
    }
    return new int[]{};
}
// O(n) time, O(n) space
```

### Анаграммы — одинаковые ли буквы в двух строках

```java
boolean isAnagram(String s, String t) {
    if (s.length() != t.length()) return false;
    Map<Character, Integer> map = new HashMap<>();
    for (char c : s.toCharArray()) map.merge(c, 1, Integer::sum);  // +1 за каждую букву s
    for (char c : t.toCharArray()) {
        map.merge(c, -1, Integer::sum);    // -1 за каждую букву t
        if (map.get(c) < 0) return false;  // в t буква встречается чаще чем в s
    }
    return true;
}
```

### Первый уникальный символ

```java
int firstUniqueChar(String s) {
    Map<Character, Integer> freq = new HashMap<>();
    for (char c : s.toCharArray()) freq.merge(c, 1, Integer::sum);
    for (int i = 0; i < s.length(); i++) {
        if (freq.get(s.charAt(i)) == 1) return i;
    }
    return -1;
}
```

## 🔹 Итог

```
HashMap = массив бакетов (Node[] table) + хэш-функция (ключ → индекс)

Ключ → hashCode() → XOR со сдвигом на 16 → & (capacity-1) → номер бакета

Коллизии → chaining: односвязный список в бакете
           при ≥ 8 нод И ≥ 64 эл. в таблице → красно-чёрное дерево

Параметры:  capacity=16,  loadFactor=0.75  →  rehash при 12 элементах
Rehash:     удваивает таблицу, O(n) — задавай capacity заранее если знаешь размер

Сложности:
  O(1)      — средний случай (хорошая хэш-функция)
  O(log n)  — худший случай с деревом (Java 8+)
  O(n)      — вырожденный случай (все в одном бакете)

Ключи — уникальны (новый заменяет старый).
Значения — могут повторяться.
Порядок — не гарантирован.
HashMap — не потокобезопасна → ConcurrentHashMap для многопоточки.
```
