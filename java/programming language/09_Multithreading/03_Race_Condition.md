# 03 — Race Condition (Гонка данных)

---

## 🔹 Демонстрация проблемы

Допустим, у нас есть простой счётчик, и два потока по 1000 раз увеличивают его на 1:

```java
class Counter {
    private int count = 0;

    public void increment() {
        count++; // выглядит как одна операция, но это не так
    }

    public int getCount() {
        return count;
    }
}

Counter counter = new Counter();

Runnable task = () -> {
    for (int i = 0; i < 1000; i++) {
        counter.increment();
    }
};

Thread t1 = new Thread(task);
Thread t2 = new Thread(task);
t1.start();
t2.start();
t1.join();
t2.join();

System.out.println(counter.getCount());
// Ожидаем: 2000
// Получаем: что-то вроде 1847, 1923, 1956... — каждый раз по-разному!
```

Почему так происходит? Чтобы понять — нужно разобраться, что `count++` делает на самом деле.

---

## 🔹 Почему count++ — это не одна операция

`count++` — это **три отдельных шага**:

```
1. READ:  прочитать текущее значение count из памяти в регистр CPU
2. ADD:   увеличить значение в регистре на 1
3. WRITE: записать новое значение обратно в память
```

Между любыми двумя шагами может произойти переключение на другой поток. Вот классический сценарий:

```
Поток A                          Поток B
─────────────────────────────────────────────────
READ count → 5
                                  READ count → 5
ADD 5+1 = 6
                                  ADD 5+1 = 6
WRITE count = 6
                                  WRITE count = 6

Результат: count = 6, но должно быть 7!
Один инкремент "потерялся".
```

Оба потока прочитали одно и то же старое значение **до** того, как кто-то из них успел его обновить. Это и называется **race condition** — результат программы зависит от того, в каком порядке и с какой скоростью потоки выполняют операции, а порядок этот недетерминирован.

> [!note] Race condition определение
> Race condition (гонка данных) — ситуация, когда корректность результата зависит от непредсказуемого порядка выполнения операций несколькими потоками над общими данными.

## 🔹 Два разных аспекта проблемы: Atomicity и Visibility

Многопоточные проблемы делятся на две принципиально разные категории. Важно их различать, потому что решаются они по-разному.

### Atomicity (атомарность)

Операция должна выполняться **целиком, без прерываний** — либо вся, либо ничего. `count++` — неатомарная операция (3 шага). Решение: `synchronized` или `Atomic*` классы.

### Visibility (видимость)

Даже если операция атомарна, изменение, сделанное одним потоком, может быть **не видно** другому потоку из-за оптимизаций CPU и компилятора.

```java
class Flag {
    private boolean running = true;

    public void stop() {
        running = false; // поток A меняет значение
    }

    public void run() {
        while (running) { // поток B может НИКОГДА не увидеть изменение!
            // делаем работу
        }
    }
}
```

Это может привести к **бесконечному циклу** — поток B будет вечно читать `running = true`, даже если поток A давным-давно установил `false`. Решение: `volatile` (см. [[05_Volatile]]) или `synchronized`.

---

## 🔹 Почему изменения "не видны" — кэши CPU

Современные процессоры не читают и не пишут напрямую в оперативную память — это слишком медленно. Вместо этого данные кэшируются в кэшах процессора (L1, L2, L3).

```
┌─────────────┐         ┌─────────────┐
│   CPU Core 1│         │   CPU Core 2│
│  ┌────────┐ │         │  ┌────────┐ │
│  │ L1 Cache│ │         │  │ L1 Cache│ │
│  │running=T│ │         │  │running=T│ │  ← у каждого ядра своя копия!
│  └────────┘ │         │  └────────┘ │
└──────┬──────┘         └──────┬──────┘
       │                         │
       └───────────┬─────────────┘
                    │
            ┌───────▼────────┐
            │  Main Memory    │
            │  running=false  │  ← поток A записал сюда,
            └─────────────────┘     но Core 2 это не увидел!
```

Поток A (на Core 1) меняет `running = false` — это сначала записывается в кэш L1 Core 1, и может не сразу "дойти" до основной памяти и до кэша Core 2. Поток B (на Core 2) продолжает читать своё кэшированное `running = true`.

## 🔹 Java Memory Model (JMM) и happens-before

Java Memory Model — это набор правил, которые описывают, **когда** изменения, сделанные одним потоком, **гарантированно** видны другому потоку.

Центральное понятие — **happens-before**. Если действие A happens-before действие B, то результаты A гарантированно видны при выполнении B.

Без специальных конструкций (synchronized, volatile, и т.д.) JMM **не гарантирует никакого порядка и видимости** между потоками — компилятор и процессор вольны переставлять и кэшировать операции как угодно, лишь бы результат был корректным для **одного** потока.

Конструкции, которые устанавливают happens-before:

```
happens-before устанавливается между:
  - выход из synchronized блока (A) и вход в synchronized на том же мониторе (B)
  - запись в volatile переменную (A) и чтение этой переменной (B)
  - Thread.start() и любая операция в запущенном потоке
  - все операции в потоке и Thread.join() в другом потоке
```

```java
// Пример: happens-before через synchronized
synchronized (lock) {
    sharedValue = 42;     // (A) запись
} // ← выход из synchronized

// В другом потоке:
synchronized (lock) {     // ← вход в synchronized на ТОМ ЖЕ lock
    print(sharedValue);   // (B) гарантированно увидит 42
}
```

## 🔹 Идемпотентность операций — почему это важно

**Идемпотентная операция** — операция, повторное выполнение которой даёт тот же результат, что и однократное.

```java
// Идемпотентно — можно безопасно повторить
account.setBalance(100); // не важно сколько раз вызвать — баланс будет 100

// НЕ идемпотентно — каждый вызов меняет результат
account.balance += 100;  // вызов 2 раза = +200, а не +100
```

В контексте многопоточности: операции вида "прочитать-изменить-записать" (`count++`, `balance += x`, `list.add(x)` если список не должен дублироваться) — НЕ идемпотентны и требуют синхронизации. Простая перезапись значения (`flag = true`) — атомарна сама по себе (для примитивов кроме `long`/`double`), но требует `volatile` для видимости.

## 🔹 Как диагностировать race condition

Race condition коварны — программа может работать правильно тысячи раз и сломаться один раз из миллиона. Признаки:

- Тест иногда (не всегда!) проходит, иногда падает
- Результат отличается между запусками одной и той же программы
- Проблема исчезает при добавлении `Thread.sleep()` или логов (это меняет тайминг и "прячет" гонку, а не решает её)
- Проблема не воспроизводится в дебаггере (пошаговое выполнение меняет тайминг потоков)

> [!warning] "Оно работает в 99% случаев" — это не работает
> Race condition не становится менее опасной от того, что проявляется редко. В продакшене с высокой нагрузкой "редкий" случай может происходить тысячи раз в день.

```
Race condition = результат зависит от непредсказуемого порядка
                  выполнения операций потоками над общими данными

Два разных аспекта:
  Atomicity  — операция должна быть неделимой (count++ это 3 шага!)
  Visibility — изменение одного потока должно быть видно другому
               (мешают кэши CPU L1/L2/L3)

JMM (Java Memory Model) — правила видимости между потоками
happens-before — гарантия "если A happens-before B, то B видит результат A"

Устанавливают happens-before:
  synchronized (выход → вход на том же мониторе)
  volatile (запись → чтение)
  Thread.start() / Thread.join()

Решения:
  Atomicity  → synchronized, Atomic* классы (см. [[06_Atomic]])
  Visibility → volatile, synchronized (см. [[05_Volatile]])

Признаки race condition: нестабильные тесты, "не воспроизводится в дебаггере"
```
